# وثيقة متطلبات منتج "بصير" (Basser) - الإصدار الأولي (MVP)

## 1. مقدمة

تحدد هذه الوثيقة المتطلبات الوظيفية وغير الوظيفية لتطبيق "بصير" MVP، مع التركيز على الميزات الأساسية لإدارة العملاء والفواتير، وتوفير تجربة مستخدم عربية احترافية.

## 2. متطلبات الميزات الوظيفية (Functional Requirements)

### 2.1. المصادقة والإعداد الأولي

| ID | قصة المستخدم (User Story) | معايير القبول (Acceptance Criteria) |
| :--- | :--- | :--- |
| FR-01 | **كـ مستخدم جديد،** أريد إعداد اسم مستخدم وكلمة مرور لحماية بياناتي المحلية. | - يجب أن تظهر شاشة الإعداد الأولي عند فتح التطبيق لأول مرة.<br>- يجب أن يتم تخزين بيانات الاعتماد بشكل آمن ومشفر محليًا.<br>- يجب أن يتم توجيه المستخدم إلى لوحة التحكم بعد الإعداد الناجح. |
| FR-02 | **كـ مستخدم،** أريد تسجيل الدخول باستخدام اسم المستخدم وكلمة المرور الخاصة بي. | - يجب أن تظهر شاشة تسجيل الدخول في المرات اللاحقة لفتح التطبيق.<br>- يجب أن يتم التحقق من بيانات الاعتماد المخزنة محليًا.<br>- يجب أن يتم توجيه المستخدم إلى لوحة التحكم عند نجاح تسجيل الدخول. |

### 2.2. إدارة العملاء (Customers)

| ID | قصة المستخدم (User Story) | معايير القبول (Acceptance Criteria) |
| :--- | :--- | :--- |
| FR-03 | **كـ مستخدم،** أريد إضافة عميل جديد ببياناته الأساسية. | - يجب أن تشمل البيانات: الاسم الكامل، رقم الهاتف، البريد الإلكتروني، العنوان (اختياري).<br>- يجب أن يتم حفظ بيانات العميل في قاعدة البيانات المحلية (Isar). |
| FR-04 | **كـ مستخدم،** أريد عرض قائمة بجميع عملائي. | - يجب أن تكون القائمة قابلة للبحث والتصفية حسب الاسم.<br>- يجب أن تعرض القائمة الاسم ورقم الهاتف لكل عميل. |
| FR-05 | **كـ مستخدم،** أريد تعديل أو حذف بيانات عميل موجود. | - يجب أن يتم تحديث أو حذف البيانات بشكل دائم من قاعدة البيانات المحلية. |

### 2.3. إدارة الفواتير (Invoices)

| ID | قصة المستخدم (User Story) | معايير القبول (Acceptance Criteria) |
| :--- | :--- | :--- |
| FR-06 | **كـ مستخدم،** أريد إنشاء فاتورة جديدة بسهولة. | - يجب أن تتضمن واجهة إنشاء الفاتورة حقولاً لـ: اختيار العميل، تاريخ الإصدار، تاريخ الاستحقاق، قائمة البنود.<br>- يجب أن يتمكن المستخدم من إضافة وحذف بنود الفاتورة (الاسم، الكمية، السعر). |
| FR-07 | **كـ مستخدم،** أريد أن يتم حساب إجمالي الفاتورة والضريبة تلقائيًا. | - يجب أن يتم حساب الإجمالي الفرعي (Subtotal) وإجمالي الضريبة (Tax Total) والإجمالي الكلي (Grand Total) بشكل فوري أثناء الإدخال.<br>- يجب أن تكون نسبة الضريبة قابلة للتعديل من الإعدادات (نسبة واحدة فقط في الـ MVP). |
| FR-08 | **كـ مستخدم،** أريد حفظ الفاتورة كمسودة أو إصدارها. | - يجب أن يتم حفظ الفاتورة بجميع تفاصيلها في قاعدة البيانات المحلية مع حالة "مسودة" أو "مُصدرة". |
| FR-09 | **كـ مستخدم،** أريد عرض قائمة بجميع فواتيري. | - يجب أن تكون القائمة قابلة للتصفية حسب الحالة (مسودة، مستحقة، مدفوعة) وحسب العميل.<br>- يجب أن تعرض القائمة رقم الفاتورة، اسم العميل، تاريخ الاستحقاق، والإجمالي الكلي. |
| FR-10 | **كـ مستخدم،** أريد عرض تفاصيل فاتورة معينة وتغيير حالتها. | - يجب أن تعرض شاشة التفاصيل جميع بنود الفاتورة والحسابات النهائية.<br>- يجب أن يتمكن المستخدم من تغيير حالة الفاتورة إلى "مدفوعة" أو "ملغاة". |

### 2.4. لوحة التحكم (Dashboard)

| ID | قصة المستخدم (User Story) | معايير القبول (Acceptance Criteria) |
| :--- | :--- | :--- |
| FR-11 | **كـ مستخدم،** أريد رؤية ملخص مالي سريع عند فتح التطبيق. | - يجب أن تعرض لوحة التحكم: إجمالي الفواتير المستحقة، إجمالي الفواتير المدفوعة، وعدد العملاء المسجلين. |

## 3. متطلبات غير وظيفية (Non-Functional Requirements)

| النوع | المتطلب |
| :--- | :--- |
| **الأداء** | يجب أن يتم تحميل جميع الشاشات في أقل من 1.5 ثانية على الأجهزة الحديثة. يجب أن تتم عمليات الحفظ والتحديث في قاعدة البيانات المحلية بشكل فوري (أقل من 500 مللي ثانية). |
| **الأمان** | يجب أن يتم تخزين بيانات الاعتماد الحساسة بشكل مشفر. يجب أن تكون جميع البيانات المالية مخزنة محليًا ولا يتم إرسالها عبر الإنترنت. |
| **قابلية الاستخدام** | يجب أن يدعم التطبيق اللغة العربية بشكل كامل (RTL). يجب أن تكون واجهة المستخدم بديهية وتتبع إرشادات تصميم الموبايل القياسية (Material Design / Cupertino). |
| **قابلية التوسع** | يجب أن يتم بناء الكود باستخدام Clean Architecture لتمكين إضافة طبقة API و Backend مستقبلاً دون إعادة كتابة منطق العمل الأساسي. |
