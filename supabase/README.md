# Supabase migrations

تحتوي هذه الحزمة على **أساس محلي غير مطبق** لبيانات Basir Accounting على Supabase. لا تنفذ أي ملف SQL مباشرة في بيئة إنتاج. يجب أولًا مراجعة كل migration، ثم تشغيلها في Supabase development branch مع اختبارات RLS والعزل بين المنظمات قبل أي تطبيق على المشروع الرئيسي.

| الترتيب | الملف | النطاق |
|---|---|---|
| 1 | `20260813220000_organization_governance.sql` | المنظمات والعضويات والملفات والإعدادات، دوال الحوكمة، وسياسات RLS |
| 2 | `20260813221000_reference_accounting_data.sql` | دليل الحسابات والسنوات المالية والعملاء والموردون، مع مفاتيح مركبة وفهارس وسياسات RLS |

الملفات لا تغطي بعد القيود المحاسبية أو الفواتير أو ZATCA أو المخزون. هذه المجالات تتطلب migrations منفصلة تتضمن تحققًا صريحًا من اتزان القيود، وعدم تغيير السجلات المرحّلة، وإغلاق الفترات.

> لا تمرر JSON الخاص بكيانات Dart مباشرة إلى PostgreSQL. تستخدم قاعدة البيانات `snake_case` و`numeric` و`jsonb` بصورة مقصودة، ويجب بناء DTO mapper صريح بين عقود Dart ذات `camelCase` وصفوف Supabase.

## التحقق المحلي المنفذ

تم تحليل ملفات SQL محليًا دون اتصال بقاعدة بيانات أو تنفيذ SQL. هذا يثبت صحة البنية النحوية فقط ولا يثبت سياسات RLS أو صلاحيات Supabase أو سلوك triggers.

## قبل التطبيق الخارجي

1. إنشاء Supabase development branch بعد الإفصاح عن التكلفة وطلب الموافقة.
2. تطبيق migrations بالتسلسل في بيئة التطوير فقط.
3. اختبار العزل بين منظمتين، ومنع إزالة آخر مالك، والعلاقات المرجعية، ودقة القيم المالية.
4. مراجعة بشرية للـSQL ونتائج الاختبار.
5. طلب موافقة مستقلة قبل تطبيق أي migration على المشروع الرئيسي.
