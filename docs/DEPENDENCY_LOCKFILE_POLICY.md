# سياسة ملفات قفل الاعتماديات والدين التقني

## نطاق السياسة

يُعد `pubspec.lock` مصدر القفل الرئيسي لتطبيق Flutter، ويجب أن يبقى متتبعًا في Git وأن يُحدّث بواسطة `flutter pub get` أو `dart pub get` المتوافق مع نسخة Flutter/Dart المعتمدة في CI. يُعد `rust/Cargo.lock` مصدر القفل لمساحة عمل Rust، ويجب تحديثه بواسطة Cargo لا بالتحرير اليدوي. أما ملفات `pubspec.lock` داخل `rust_builder/cargokit/build_tool` و`tools/repository_cleaner` فهي أقفال لمشروعات فرعية مستقلة، ويجب التحقق منها ضمن CI الخاص بكل مشروع بدل خلطها بقفل التطبيق الرئيسي.

## خط الأساس المعتمد

تستخدم workflows نسخة Flutter `3.44.9`. يتطلب `pubspec.lock` الحالي Dart `>=3.10.0 <4.0.0` وFlutter `>=3.35.0`. لذلك تم رفع الحد الأدنى المعلن في `pubspec.yaml` إلى Dart `>=3.10.0 <4.0.0` حتى لا يعلن المشروع توافقًا أوسع من القفل الفعلي وبيئة CI.

تم تحويل الاعتماديات المباشرة غير المقيدة `http: any` و`path: any` و`riverpod: any` إلى قيود دنيا متوافقة مع النسخ المقفلة الحالية: `^1.6.0` و`^1.9.1` و`^2.6.1`. لم يُعدّل `pubspec.lock` يدويًا؛ فالقيم المقفلة الحالية تطابق القيود الجديدة، ويجب أن تثبت عملية `flutter pub get` في CI عدم وجود diff.

## قواعد التحديث

أي تحديث اعتمادية يجب أن يغير manifest والقفل الناتج معًا، وأن يمر بفحص حلّ الاعتماديات، وفحص الاختبارات، وفحص الترخيص والأمان. لا تُقبل تغييرات يدوية في الأجزاء العابرة من lockfile، ولا تُستخدم أوامر الترقية الشاملة إلا في PR مخصص يوضح نطاق التغيير والتأثير المتوقع.

قبل رفع أي نسخة رئيسية، يجب تسجيل سبب التغيير، توافق Flutter/Dart، تغييرات API المحتملة، وفحوص الرجوع. يجب عزل تحديثات Rust عن تحديثات Flutter متى أمكن، لأن كل مساحة عمل لها قفل ودورة تحقق مختلفة.

## الدين التقني المتبقي

توجد ملفات `*.isar.lock` في جذر المستودع تبدو كملفات قفل runtime أو آثار اختبارات، وليست ملفات قفل مدير حزم. لا تُحذف تلقائيًا في هذه الحزمة حفاظًا على التاريخ؛ يلزم أولًا التحقق من أنها ليست fixtures مطلوبة، ثم نقلها أو إزالتها في PR مستقل مع تحديث `.gitignore` واختبارات التشغيل.

يبقى تعارض `flex_color_picker` السابق مرتبطًا ببيئة Flutter الأقدم `3.35.5` وبالنسخة `3.8.0` التي تتطلب Flutter `>=3.38.0`. بعد توحيد CI إلى `3.44.9` يجب إعادة توليد القفل في بيئة CI، ثم اعتماد النتيجة فقط إذا كانت الفحوص والتطبيق متوافقين. لا ينبغي رفع النسخة إلى `3.8.0` تلقائيًا لمجرد أن الحل أصبح ممكنًا؛ ذلك تحديث وظيفي منفصل يحتاج مراجعة.

## قرار هذه الحزمة

الإجراء المنفذ هو `FIX` لحدود SDK والقيود غير المحددة، مع `KEEP` لملفات القفل الحالية إلى أن تعيد CI توليدها وتثبت عدم وجود drift. ملفات Isar runtime مصنفة `INVESTIGATE` ثم `ARCHIVE` أو `DELETE` فقط بعد موافقة ومراجعة اعتمادها.
