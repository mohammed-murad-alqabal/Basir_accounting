## السياق

كان التحقق من قيد اليومية يقتصر أساسًا على توازن إجمالي المدين والدائن، ويمكن أن تمر سطور فارغة أو تحمل مدينًا ودائنًا معًا إذا بقي المجموع متوازنًا. كما تكرر تحقق التوازن في بعض مسارات الفواتير، لكن خدمة `postJournalEntry` لم تكن تستدعي حارس نطاق يغطي بنية السطر والعملات. لا يكفي إخفاء فعل في واجهة المستخدم أو تحقق منشئ فاتورة لحماية أثر الدفتر عند وجود مسار خدمة آخر أو retry.

## القرار

ينفذ `JournalEntryValidator.ensurePostable` داخل `AccountingService.postJournalEntry` **قبل** أي قراءة/كتابة تؤدي إلى أثر مرحل، ويعيد `JournalEntryValidationException` يحمل رموز فشل ثابتة. يتحقق الحارس من الحد الأدنى للسطرين، وصحة الحساب، وعدم السلبية، وحصرية المدين أو الدائن، والمبلغ الموجب، والتوازن، واكتمال سياق العملة الأصلية. تبقى خدمة السنة المالية مسؤولة عن قفل الفترة، وتبقى طبقات الصلاحيات/idempotency مسؤولة عن نطاقها الخاص.

يستخدم مسار عكس القيد مرجعًا عكسيًا مشتقًا `RV-<original-reference>` ويرفض إنشاء عكس ثانٍ بالمرجع نفسه. لا يحل ذلك محل علاقة reversal مستقلة في schema مستقبلي، لكنه يمنع تكرار العكس في الحد الحالي.

## النتائج

| النتيجة | الأثر |
|---|---|
| قبول قيد مرحل | لا يكتب المستودع قيدًا يخالف invariants الأساسية. |
| خطأ نطاقي ثابت | تتعامل الواجهة والاختبار والتدقيق مع code بدل نص exception هش. |
| تحقق مكرر آمن | قد تستدعي مسارات الفواتير الحارس قبل الخدمة، ثم تستدعيه الخدمة مرة أخرى؛ لا يغير ذلك النتيجة ولا يكتب أثرًا. |
| قيد العكس | يمنع التكرار المرجعي، لكن سيحتاج مخطط البيانات لاحقًا إلى `reversesEntryId` وعقد idempotency أقوى. |

## البدائل المرفوضة

رفضنا الاقتصار على `isBalanced` لأن التوازن لا يمنع سطرًا صفريًا أو مزدوج الطرف. ورفضنا فرض القواعد داخل UI أو repository فقط؛ الأولى قابلة للتجاوز والثانية لا تملك سياق الترحيل/الفترة/التدقيق الكافي.

## التحقق

تغطي اختبارات `journal_entry_validator_test.dart` حالات القبول والحد الأدنى وحصرية الطرفين والسلبية وتوازن القيد وسياق العملة والحالة voided. ويجب أن تتبعها اختبارات تكامل لخدمة الترحيل والمستودع قبل جعل REQ-ACC-001 إلى REQ-ACC-003 بحالة `VERIFIED`.
