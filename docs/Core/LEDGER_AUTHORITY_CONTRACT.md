# عقد سلطة دفتر الأستاذ

> **PostgreSQL هو المصدر السلطوي الوحيد للقيود المنشورة.** لا تمثل قاعدة Isar إلا مسودات محلية وذاكرة cache لإيصالات خادم مؤكدة.

## 1. حدود الحالة

| نوع الحالة | المكان المسموح | القاعدة |
|---|---|---|
| مسودة لم تُنشر | Isar | يمكن حفظها محليًا، ولا تؤثر في الرصيد النهائي. |
| أمر إرسال متعذر نقله | Isar outbox | يحتفظ بالحمولة وإحصاء المحاولات، ولا يساوي قيدًا منشورًا. |
| قيد `Posted` | PostgreSQL فقط | لا يصبح نهائيًا إلا بعد معاملة `post_ledger_entry`. |
| نسخة محلية لقيد منشور | Isar cache | لا تُكتب إلا من `LedgerPostReceipt` مكتمل يحمل `entry_id` وhash ووقت النشر. |

`LedgerAuthorityPolicy` يرفض أي `addJournalEntry` محلي لحالة `Posted` ما لم يمرر التنفيذ عبر `cacheAuthoritativeJournalEntry` بعد receipt خادمي. لذلك لا يجوز استنتاج النجاح من حالة اتصال العميل أو من مزامنة Last-Write-Wins.

## 2. بروتوكول النشر

1. تنشئ طبقة التطبيق قيدًا متوازنًا وتتحقق من الفترة المالية.
2. تشتق `SupabaseLedgerGateway` معرف عملية UUID v5 ثابتًا من معرف القيد المحلي. يظل المعرف نفسه في كل إعادة محاولة.
3. تستدعي البوابة RPC المحمي `post_ledger_entry` عبر Supabase. لا يوجد اتصال PostgreSQL أو سر قاعدة بيانات داخل Flutter.
4. تتحقق المعاملة من JWT، ودور `app_metadata.role`، والاتزان، والفترة، والحسابات، وhash الحمولة، ثم تدرج الرأس والسطور وسجل التدقيق atomically.
5. تعيد PostgreSQL receipt يتضمن `entry_id` و`entry_hash` و`previous_hash` و`posted_at` و`idempotent_replay`.
6. بعد receipt فقط، تخزن الخدمة نسخة cache في Isar مع `authoritativeEntryId`، ثم تحدّث واجهة المستخدم.

| النتيجة | السلوك المطلوب |
|---|---|
| receipt ناجح | cache محلي مؤكد. |
| إعادة إرسال للحمولة نفسها | تعاد receipt نفسها مع `idempotent_replay=true` ولا تتكرر السطور أو التدقيق. |
| خطأ شبكة أو مهلة قبل receipt | يوضع الأمر في outbox ويُعرض كـ queued، وليس posted. |
| رفض Postgres (تفويض، فترة مغلقة، عدم اتزان، تضارب الحمولة) | يُعاد الخطأ للمستخدم/التشغيل فورًا؛ لا يوضع في outbox. |

## 3. عقد idempotency وسلامة التدقيق

يستخدم `p_entry_id` كمفتاح عملية وحيد. تحتفظ الدالة بـ `operation_hash` مشتق من كل الحمولة الجوهرية. إذا عاد المعرف نفسه مع hash مطابق فهي إعادة آمنة؛ وإذا تغيرت الحمولة يخرج الاستدعاء بالخطأ `LEDGER_OPERATION_PAYLOAD_CONFLICT` ولا يُسمح بتبديل حقيقة منشورة.

تستخدم دالة RPC `SECURITY DEFINER` مع `search_path` مقيدًا، وتتحقق من claims JWT قبل الكتابة. الأدوار المسموح لها بالنشر هي `owner` و`admin` و`accountant`. يمنع `REVOKE` التنفيذ العام، ويعاد منح RPC لدور `authenticated` فقط؛ تحقق الدالة من الدور الوظيفي، وليس من قيمة تمررها حمولة العميل.

## 4. متطلبات التشغيل

| عنصر | شرط الإطلاق |
|---|---|
| الترحيل | تطبيق `20260110090000_authoritative_ledger_posting.sql` في بيئة اختبار ثم إنتاج عبر مسار الترحيلات المعتمد. |
| الحسابات | الحسابات المرسلة بغير UUID تُسقط حتميًا إلى namespace خادمي؛ يلزم أن تكون الحسابات المقابلة seeded في PostgreSQL قبل النشر. |
| المزامنة | لا تعيد `SyncService` رفع أو مزج journal entries بمنهج LWW؛ دوره تشغيل `LedgerOutboxService.flush()` فقط. |
| المراقبة | يشغّل `ledger_health_check.sql` ويُراجع تقرير `reconcile_ledger.py` قبل أي معالجة بيانات. |
| التراجع | لا يحذف قيدًا منشورًا. يستخدم قيد عكسي موثقًا بعد تحقق محاسبي. |

## 5. أدلة CI

`./scripts/ci_authoritative_ledger.sh` ينشئ مخططًا نظيفًا ثم يثبت: الذرية، الاتزان، التفويض، idempotency، رفض تضارب الحمولة، سلامة الصحة، وأن المصالحة تعطي Postgres الأولوية. ويشغّل مسار Flutter المستهدف اختبارات تمنع الكتابة المحلية المنشورة.
