# استيراد وتكافؤ موجة Profile وBusinessSettings

## حدود التنفيذ

يضيف هذا التغيير أدوات صريحة فقط، هي `DriftSettingsMigrator` و`DriftSettingsParityVerifier`. لا تُستدعى من Providers أو واجهة المستخدم أو خدمة المزامنة. يظل Isar مصدر القراءة والكتابة في التطبيق؛ لا يغير الاستيراد أي صف في Isar، ولا يفعّل shadow-read أو canary أو dual-write.

## الاستيراد القابل للإعادة

| الشريحة | مصدر Isar | وجهة Drift | مفتاح الاستبدال | checkpoint |
|---|---|---|---|---|
| Profile | كل `profileModels` بترتيب نطاق المستخدم ثم `id` | `ProfileStorage` | `scopeKey` لكل مستخدم | `settings-profiles-v1` |
| BusinessSettings | كل `businessSettingsModels` بالترتيب نفسه | `BusinessSettingsStorage` | `scopeKey` لكل مستخدم | `settings-business-settings-v1` |

ينفذ المستورد upsert في دفعات، ويحفظ checkpoint غير مكتمل بعد كل دفعة ثم checkpoint مكتمل عند النجاح. إعادة التشغيل تعيد قراءة لقطة المصدر وتنفذ upsert بالمعرف والنطاق، ولذلك لا تنشئ تكرارات في Drift. لا تُستخدم checkpoint لتجاوز سجلات مصدر قد تكون تغيرت؛ فهي دليل تقدم تشخيصي، وليست بديلًا عن إعادة قراءة لقطة متسقة.

## parity وموانع التقدم

تقرأ أداة parity جميع سجلات المصدر والهدف، وتقارن العدد وبصمة canonical حتمية تشمل جميع حقول العقد، بما فيها `SyncStatus` و`serverUpdatedAt` والحذف الناعم. القراءة الكاملة من Drift ضرورية لكشف سجل هدف قديم أو زائد لا يظهر عند الاستعلام بمستخدم موجود في المصدر.

| حالة الفحص | النتيجة | القرار |
|---|---|---|
| العدد والبصمة متطابقان، ولا نطاقات غامضة | `isClean = true` | يسمح بالانتقال إلى تصميم telemetry للـshadow-read فقط |
| اختلاف عدد أو بصمة | `isClean = false` | حجب canary والتحقيق في التحويل أو بيانات المصدر/الهدف |
| أكثر من Profile أو BusinessSettings للمستخدم نفسه في Isar | نطاق غامض ببصمة غير كاشفة | حجب التقدم؛ Drift يملك سجلًا واحدًا فقط لكل نطاق |
| سجل Drift زائد | اختلاف عدد/بصمة | حجب التقدم؛ لا يوجد حذف تلقائي في المستورد |

لا تُعرض userIds أو payloads في التقرير التشخيصي. النطاقات الغامضة تمثل كبصمات تشخيصية فقط، وهي ليست hash أمنيًا أو وسيلة لمصادقة البيانات.

## التحقق المنفذ

تغطي الاختبارات الدفعات، المصادر الفارغة، batch size غير الصحيح، checkpoints، قابلية إعادة التشغيل، parity السليم، السجل الهدف الزائد، تعدد المصدر في نطاق واحد، واختبار تكامل يفتح Isar مؤقتًا وSQLite في الذاكرة ثم يثبت أن المصدر لم يتغير بعد الاستيراد.

> لا تعني الاختبارات نجاح ترحيل بيانات تشغيلية. قبل أي shadow-read يجب تشغيل الأداتين يدويًا على لقطة معقمة ومراجعة، والاحتفاظ بتقرير نظيف، ثم إضافة telemetry بلا payload قبل تفعيل canary منفصل لكل repository.
