# خطة إصلاح شاملة لمشروع Basir Accounting

**مرجع الخطة:** تقرير المراجعة عند commit `477676dc4fb8031609d782c9914dd6ffd9a97a32`.
**الهدف:** نقل المشروع من حالة **NO-GO** إلى حالة قابلة لإعادة التحقق، دون إخفاء فشل CI أو تغيير مصدر الحقيقة المحاسبي بلا خطة بيانات واختبارات rollback.

## مبدأ التنفيذ

يُنفذ الإصلاح على موجات قصيرة. كل موجة تملك نطاقًا واضحًا، ومالكًا، وPRات محددة، واختبارات قبول. لا يجوز البدء في إصلاحات محاسبية واسعة قبل جعل toolchain وCI قابلين للتشغيل؛ وإلا ستختلط أخطاء البيئة بأخطاء الكود. ولا يجوز إعلان الجاهزية بسبب نجاح اختبارات وحدة فقط؛ بل يلزم دليل على SHA واحد، وartifact، وبيانات معقمة، ونتيجة بوابات الأمن والجودة.

## الموجة 1 — توحيد Flutter/Dart وحل التبعيات

### 1.1 اختيار نسخة حاكمة

اختَر نسخة Flutter واحدة تحقق متطلبات كل الحزم الحالية. بما أن lockfile الحالي يتطلب Dart `>=3.13.0` وFlutter `>=3.47.0`، فالخيار الأول هو اعتماد Flutter `>=3.47.0` مع تثبيت revision وchecksum معروفين. الخيار البديل هو تخفيض `flex_color_picker` إلى إصدار متوافق، ثم إعادة حل كل التبعيات باختبار شامل. لا يجوز إبقاء الخيارين مختلطين.

سجّل القرار في وثيقة Toolchain تتضمن Flutter وDart وJava وRust وإصدارات generator. اجعل `pubspec.yaml` و`pubspec.lock` و`.metadata` وworkflows متوافقة مع القرار نفسه.

### 1.2 إصلاح Action المركبة

عدّل `.github/actions/setup-flutter/action.yml` ليقبل `flutter-version` أو revision وchecksum كمدخلات فعلية. لا تترك `3.35.5` hard-coded. إذا اختيرت طريقة Git clone في production gate، فإما تعميمها على كل workflows أو استخدام Action واحدة مشتركة؛ لا تحتفظ بمسارين مستقلين للنسخة.

### 1.3 تثبيت lockfile

بعد اعتماد النسخة، نفّذ resolver باستخدام نفس Flutter المعلن، ثم راجع diff في `pubspec.lock`. يجب أن يفشل CI إذا عدّل `flutter pub get` lockfile. افحص كذلك قيد SDK النهائي في نهاية lockfile.

### معيار قبول الموجة 1

- `flutter pub get` ينجح في Analysis وFlutter CI وProduction Gate وDocumentation Governance.
- يظهر في السجل Dart ضمن المجال `>=3.13.0` إذا بقي `flex_color_picker 4.0.0`.
- لا يعاد توليد lockfile بعد `pub get`.
- لا توجد نسخة Flutter أخرى hard-coded في workflow أو Action.
- ينجح `dart run build_runner build --delete-conflicting-outputs` دون diff غير متوقع.

## الموجة 2 — Rust quality والأمن

### 2.1 إصلاح formatting أولًا

نفّذ `cargo fmt --all` في فرع مستقل، راجع diff، ثم أعد تشغيل Rust Integration وProduction Gate. لا تخلط تغييرات formatting مع منطق محاسبي أو تحديثات كبيرة.

### 2.2 معالجة rustls وwnaf

نفّذ:

```bash
cd rust
cargo tree -i rustls
cargo tree -i wnaf
```

حدد الحزمة الأم التي تسحب `rustls 0.23.42` و`wnaf 0.14.0`. حدّث الحزمة الأم أو استبدلها أو أزل الاعتماد غير الضروري، ثم أعد توليد `Cargo.lock`. يجب أن تكون الأولوية لإزالة `wnaf` المسحوبة، ثم معالجة advisory `RUSTSEC-2026-0285`.

لا تضف `--ignore` جديدًا إلا باستثناء مؤقت يحتوي رقم issue، المالك، سبب عدم وجود إصلاح متاح، تقييم الخطر، وتاريخ انتهاء قريب. يجب حذف الاستثناءات التي انتهت تواريخ مراجعتها في 12 سبتمبر.

### معيار قبول الموجة 2

- `cargo fmt --all -- --check` ناجح.
- `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings` ناجح.
- `cargo audit --deny warnings` ناجح دون تجاهل `wnaf` المسحوبة.
- `cargo test --workspace --all-targets --all-features --locked` واختبارات doc ناجحة مع PostgreSQL test service.
- كل advisory مستثنى موثق ومؤقت ولا يخفي حالة غير معروفة.

## الموجة 3 — اعتماد Ledger Authority فعليًا

### 3.1 اعتماد ADR ملزم

أنشئ أو اعتمد ADR يحدد هل Rust/PostgreSQL هو المصدر الحاكم أم Isar. لا تقبل الخطة وضعًا مختلطًا غير موثق. بناءً على `LedgerAuthorityPolicy` الحالية، الاتجاه المقصود هو أن PostgreSQL/Rust يثبت القيد ثم يخزن التطبيق cache لنتيجة سلطوية.

حدد الحالات التالية صراحة: `draft`, `pending_authoritative_post`, `posted_authoritative`, `pending_zatca`, `failed`. عرّف الحقول الإلزامية للقيد المرحّل: `authoritativeEntryId`, `hash`, `postedAt`, receipt version، وsource idempotency key.

### 3.2 منع الكتابة المحلية لـPosted

طبّق `LedgerAuthorityPolicy.assertLocalWriteAllowed` داخل كل repository أو اجعل API التخزين لا يقبل `Posted` إلا عبر دالة cache سلطوية تتحقق من receipt. يجب ألا يستطيع `AccountingService.postJournalEntry` استدعاء `addJournalEntry` المحلي لقيد نهائي.

حوّل الكتابة المحلية إلى أحد الآتي:

- حفظ مسودة فقط.
- إرسال command إلى gateway السلطوي.
- تخزين cache بعد التحقق من receipt.

لا تعتمد على convention أو تعليق؛ يجب أن يكون الفشل runtime وtestable.

### 3.3 إزالة المسارات المنافسة

اجعل `AccountingService.postInvoice` و`SalesInvoicePostingService` يمران عبر use case واحد. إذا بقي أحدهما adapter للتوافق، يجب أن يستدعي المصدر نفسه ولا يكتب مباشرة. راجع كل `JournalEntryStatus.posted` وكل `JournalEntryModel.fromEntity` في مسارات التخزين.

### 3.4 idempotency والتنافس

أضف idempotency key مشتقًا من tenant وsource document وsource id. نفّذ قيدًا فريدًا على receipt والوثيقة المصدر. في حال إعادة إرسال نفس الأمر، أعد receipt السابق. في حال وصول الأمر من tenant آخر أو actor غير مخول، ارفضه دون كتابة.

### معيار قبول الموجة 3

- لا يمكن حفظ `Posted` محليًا بلا receipt سلطوي.
- اختبار مسار Dart القديم يفشل قبل أي كتابة أو يتحول إلى use case الجديد.
- إرسال نفس invoice مرتين بالتوازي ينتج قيدًا واحدًا وتحديث رصيد واحد.
- إعادة محاولة بعد timeout تعيد النتيجة السلطوية ولا تضاعف القيد.
- يوجد اختبار يثبت أن `LedgerAuthorityPolicy` تُستدعى، وليس اختبارًا للسياسة معزولًا فقط.
- Trial Balance وGeneral Ledger يقرآن نفس مصدر الحقيقة.

## الموجة 4 — التفويض وعزل نطاق البيانات

### 4.1 استبدال `canPost` بسياق مخول

غيّر عقد الترحيل من boolean يرسله المستدعي إلى `AuthorizationContext` يحتوي actor id وtenant id وrole وpermissions وwarehouse scope. تتحقق الخدمة من Permission، ملكية المستند، الفترة المالية، وحالة المستخدم. يبقى فحص الشاشة لتحسين UX فقط.

طبّق نفس السياسة على العكس، قفل الفترة، إدارة المستخدمين، النسخ والاستعادة، التصدير، وإدارة الحسابات.

### 4.2 حماية bypass

احذف `bypassCognitive` من public methods أو اجعله capability داخلية لا يمكن إنشاؤها من طبقة الواجهة. إذا كان bypass مطلوبًا للترحيل السلطوي، فيجب أن يتطلب actor موثقًا، سببًا، ticket أو approval، وسجلًا تدقيقيًا غير قابل للحذف.

### 4.3 منع المستودعات بلا هوية

لا تنشئ مستودعًا بــ`userId: null`. استخدم `requireAuthenticatedTenant()` داخل provider، وأعد حالة رفض واضحة عند غياب الهوية. بالنسبة إلى الضيف، اختر منع الكتابة الدائمة أو منح UUID خاصًا بالجلسة مع نطاق لا يختلط بالمستخدمين.

### 4.4 إصلاح هوية الضيف

استبدل `id: 'guest'` بمعرف UUID محفوظ للجلسة، أو امنع عمليات إنشاء الفواتير والحسابات للضيف. أضف اختبار جلستين ضيف منفصلتين، واختبار إعادة تشغيل، واختبار تحويل الضيف إلى مستخدم دون ترك سجلات مجهولة أو مشتركة.

### معيار قبول الموجة 4

- استدعاء الخدمة مباشرة من مستخدم بلا Permission يرفض دون كتابة.
- تمرير `canPost: true` أو أي قيمة مشابهة لا يمنح صلاحية بذاته.
- لا توجد queries نطاقية تعمل عند userId null.
- لا يرى ضيف بيانات ضيف آخر.
- لا يستطيع actor تغيير مستند أو قيد tenant آخر.
- كل bypass موثق في audit ويُرفض إذا غاب السبب أو capability.

## الموجة 5 — المصادقة وسياسة كلمات المرور

### 5.1 إلغاء reset غير الموثق

احذف `changePasswordWithoutOldPassword` إن لم تكن مستخدمة. إذا كانت مطلوبة، صمم token موقّعًا أو opaque token عشوائيًا بمدة وانتهاء واستخدام واحد وربط بالمستخدم. يجب عدم الاكتفاء باسم المستخدم.

### 5.2 منع مسح secure storage

أزل `secureStorage.deleteAll()` من مسار غياب marker. أنشئ migration versioned. عند وجود بيانات قديمة بلا marker، احفظها ثم نفذ migration قابلًا للتراجع، أو اعرض recovery صريحًا. أضف اختبار upgrade من كل schema تاريخي معروف.

### 5.3 توحيد سياسة كلمة المرور

اعتمد حدًا أدنى واحدًا، ويفضل أن يتوافق مع متطلبات الأمن الحالية بثمانية أحرف على الأقل، مع حد 72 بايت UTF-8 وبcrypt cost 12. ضع القاعدة في validator واحد تستخدمه create، change، reset، وواجهة القوة. حدّث ADR وSECURITY.md والاختبارات معًا، ولا تترك اختبارات الستة أحرف كمرجع سلوكي.

### معيار قبول الموجة 5

- لا يوجد مسار reset بلا إثبات امتلاك token أو كلمة قديمة.
- اختبار الترقية لا يفقد username أو hash أو user id.
- فشل أي write في منتصف إنشاء الحساب لا يترك حسابًا جزئيًا قابلًا للتسجيل.
- الحد الأدنى موحد في كل المسارات.
- اختبارات bcrypt والـlegacy migration والحد UTF-8 ناجحة.
- سجلات المصادقة الحساسة تحتوي actor/time/action/target دون كشف كلمة المرور أو token.

## الموجة 6 — الدقة المالية وZATCA

### 6.1 Money type دقيق

حوّل `PostingImpactLine.amount` إلى `Decimal` أو minor units مع `currencyCode` وscale. لا تستخدم `toDouble()` في قرار قبول القيد. ثبّت سياسة rounding لكل عملة.

### 6.2 مطابقة الخطوط

لا تكتفِ بمجموع المدين والدائن. اربط كل preview line بالحساب أو الأثر المتوقع، ونوع الأثر، والاتجاه، والعملة، والمبلغ. ارفض تبديل التوزيع حتى لو تساوى المجموع.

### 6.3 حالة ZATCA موثوقة

حدد هل receipt ZATCA شرط قبل `posted_authoritative` أو مرحلة لاحقة. إذا كان لاحقًا، أضف durable outbox وإعادة محاولة وdead-letter ومراقبة. لا تمتص فشل Rust بواسطة `debugPrint` بعد تثبيت قيد مكتمل. يجب أن تظهر حالة الفاتورة في التقارير وفق سياسة واضحة.

### معيار قبول الموجة 6

- حالات `0.1 + 0.2` والـrounding والعملات المتعددة تُحسم بدون float tolerance.
- preview بخطوط مختلفة ومجموع متساوٍ يُرفض.
- فشل ZATCA ينتج حالة معروفة قابلة لإعادة المحاولة ولا يدعي الامتثال.
- retry لا يكرر الفاتورة أو القيد أو receipt.

## الموجة 7 — الاختبارات والهجرة والأدلة

### 7.1 إزالة الاختبارات المتخطاة

أعد تصميم `ExcelImportService` لحقن FilePicker أو adapter قابل للاختبار. أعد اختبار الأداء إلى CI بعد معالجة سبب عدم الثبات أو انقله إلى job أداء منفصل مع baseline. كل skip مؤقت يجب أن يملك issue وowner وموعد إغلاق.

### 7.2 اختبارات التخزين الحقيقي

أضف تكاملًا بـIsar/Rust/PostgreSQL يثبت transaction، idempotency، receipt، ownership، وrollback. لا تعتبر fake gateway دليلًا على التزام التخزين الحقيقي.

### 7.3 Migration parity

أنشئ snapshot معقمًا له provenance وSHA. قارن عدد السجلات، المجاميع، الأرصدة، حالات القيود، hash chains، ونتائج التقارير بين Isar وDrift/PostgreSQL. اختبر rollback والبيانات التالفة. أولوية المقارنة للمخزون وحركاته والفواتير والقيود.

### 7.4 Web وAndroid artifacts

إذا كان Web مدعومًا، عالج مشكلة أرقام schema المولدة بطريقة migration معتمدة ولا تعدل `.g.dart` عشوائيًا. إذا لم يكن مدعومًا، أزل claim وjob. شغّل Android release candidate في CI مع SDK معلوم، واختبر التطبيق من install نظيف وترقية فعلية.

### معيار قبول الموجة 7

- لا skips غير موثقة.
- `flutter test --coverage` وRust tests ينجحان على SHA واحد.
- threshold التغطية يقاس من artifact فعلي، لا من تقرير تاريخي.
- migration parity وrollback ناجحان على snapshot معقم.
- Web/Android artifacts قابلة للتشغيل أو موصوفة بوضوح كمنصات غير مدعومة.

## الموجة 8 — الوثائق والصلاحيات والنظافة

### 8.1 إصلاح الروابط الحاكمة

حدّث README وAUTHORITY_MODEL وSECURITY_REQUIREMENTS وكل فهارس الوثائق لتشير إلى الملفات الفعلية تحت `docs/reports/audits/bkip-2026-08/` أو انقل الملفات إلى مسار واحد. لا تترك مراجع إلى `.kiro/specs/active` أو `docs/Strategic` غير الموجودة.

أضف فحصًا محليًا للروابط النسبية يستثني الروابط الخارجية بصراحة، ويصدر قائمة fail-closed للملفات الحاكمة فقط. صنف الروابط التاريخية في `archive` بدل تركها تبدو حية.

### 8.2 فصل الادعاءات التاريخية

عدّل `CHANGELOG.md` ليصف التغيير التاريخي مع SHA وRun ID. انقل عبارة “Production Ready” وأرقام الاختبارات القديمة إلى وثيقة archive واضحة، أو اربطها بدليلها وتاريخ صلاحيتها. لا تتعارض وثيقة نشطة مع `AUTHORITY_MODEL` الذي يحظر claims غير المؤيدة.

### 8.3 تقليل صلاحيات Android

راجع كل تصريح Android مقابل feature حالي. أزل CALL_PHONE وSEND_SMS والموقع والصوت والوسائط غير اللازمة، أو أنشئ متطلبات واختبارات وشرحًا لسببها. اجعل الطلب runtime عند الحاجة فقط. راجع `allowBackup` مع نموذج تهديد وبيانات محاسبية، وأضف سياسة backup/restore تمنع تسريب أو خلط نطاقات البيانات.

### معيار قبول الموجة 8

- فحص الوثائق ينجح دون مسارات حاكمة مفقودة.
- كل وثيقة حاكمة لها owner وstatus وlast_verified_sha وreview_due صحيح.
- لا يوجد claim إنتاجي فعال بلا SHA وartifact ومالك نطاق.
- أذونات Android مبررة ومستخدمة أو محذوفة.
- backup/restore مغطى باختبار عزل واسترجاع.

## بوابة إعادة التقييم

لا ينتقل المشروع إلى **GO** إلا إذا تحققت جميع البنود التالية على SHA واحد:

| البند | دليل القبول |
|---|---|
| Toolchain | `flutter pub get` ناجح وlockfile ثابت ونسخة موحدة |
| Flutter | format وanalyze وtest وcoverage وAndroid smoke artifact ناجحة |
| Rust | fmt وclippy وunit/integration/doc tests ناجحة |
| Security | RustSec وDependabot وsecret scan بلا مخاطر غير معالجة |
| Ledger | لا Posted محلي بلا receipt، مع idempotency وownership وrollback |
| Authorization | direct service tests ترفض كل actor غير مخول |
| Authentication | reset/migration/password policy tests ناجحة |
| Financial precision | Decimal/currency/line matching tests ناجحة |
| ZATCA | حالات failure/retry/receipt مثبتة ولا توجد claims غير مدعومة |
| Migration | parity snapshot وrollback ناجحان |
| Documentation | الروابط الحاكمة وmetadata والclaims ناجحة |
| Mobile security | أذونات مبررة وbackup policy واختبارات عزل ناجحة |
